# ADR-0015 · 编辑工作流（同步-解析-入库三段制与暂存可见性）

- 状态：Accepted
- 日期：2026-08-29
- 关联：ADR-0001（Company Registry 人工入册）、ADR-0008（upsert 幂等）、ADR-0013（本地优先）、ADR-0014（LLM 移出同步关键路径）、spec09、spec10

## 背景

用户在 spec07-09 推进期间补充需求：手动数据入库拆成三步——先拉取新数据（同步）、再有 LLM 解析、人工确认或编辑后入库。这与此前两条既定决策相冲突，需要重新权衡：

1. ADR-0014：同步关键路径零 LLM（当时的动因：同步必须快、可靠、零成本）。
2. 同步即上架：新数据写完 D1 对访客立即可见（当时的动因：无人值守日报时效）。

## 决策

1. **三段制 + 暂存**：同步段只把新数据写入暂存态（items/sources.published=0，零 LLM）；解析段由管理员按需触发（Worker 内调 LLM，产出归属建议与候选公司，均为"建议"不直接生效）；入库段经 /review 审核页人工确认/编辑后原子发布（published=1 + 应用建议）。访客只见 published=1。
2. **ADR-0014 缩窄而非推翻**：「同步段零 LLM」不变（同步仍然快、可靠、可无人值守）；LLM 回到 Worker 但在**独立的解析段**（管理员触发、MAX_LLM_PER_RUN 限流、幂等可重跑）。原 spec09 的离线脚本保留，定位收窄为存量数据回填。
3. **白名单不变**：候选公司只进 company_candidates 表（带 source_item_id 溯源）与审核页呈现；入册唯一通道仍是人工编辑 data/companies.yaml → gen:registry → sync（ADR-0001）。Worker 不写 repo 文件。
4. **时效取舍**：未确认的暂存数据对访客不可见——站点停留在上一期已确认内容。此为用户口径「人工确认后入库」的直接推论，个人编辑工具接受该代价。

## 后果

- items/sources 需要发布态列与一次性迁移（DEFAULT 1 保证存量不受影响）。
- upsert 语义变化：DO UPDATE 不含 published（重同步不翻转状态）。
- Worker 重新依赖 LLM secret/vars（LLM_API_KEY 等），解析段成本与失败面集中在 /api/parse，不影响同步可用性。
- 审核页成为每日流程的必经环节：sync → parse → review → publish。
- 若未来要恢复全自动时效，只需把 publish 挂到解析完成后自动执行（预留的降级路径），架构不变。
- **2026-09-09 修订（ADR-0016）**：上述降级路径已启用——定时链路（cron）在解析完成后自动入库，异常（同步失败 / 解析失败 / 整轮零成功 / 解析进行中）留人工；本 ADR 定义的手动链路（sync → parse → review → publish）语义不变，「入库恒人工」仅约束手动链路。
