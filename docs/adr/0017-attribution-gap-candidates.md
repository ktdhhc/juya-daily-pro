# ADR-0017 · 归属缺口兜底（无主导判定与候选闭环）

- 状态：Accepted
- 日期：2026-09-09
- 关联：ADR-0001（Company Registry 唯一闸门、人工入册）、ADR-0014（单段归属、无 RAG）、ADR-0015/0016（编辑工作流与定时自动入库）、spec16

## 背景

段一确定性匹配只回答"这条提到了哪些在册公司"，不回答"主角是谁"。当主角公司不在 Registry、而正文顺带提到在册公司时：

1. 条目被归属给顺带公司，第二段 LLM 被响应校验强制从候选中挑一个主导 → 出现"OpenRouter 主导 Inception Labs 新闻"这类错误徽章（生产实测：多家命中 374 条中 73 条标题不含任何命中公司）。
2. 现有候选公司流程只覆盖"零命中"条目，这类条目**不产生候选**，编辑既看不到缺口，也无法攒进名单批量入册。

## 决策

1. **允许 LLM 判定"候选里没有主角"**：主导判定 prompt 与响应校验支持 `primary_company_id: null`；合法判定与"响应不合法"两条路径必须可区分。
2. **无主导不硬选**：这类条目保留段一命中的归属行、角色全部留空（无主次徽章），**不落归属建议**（proposal）——避免为"无主导"扩展建议的角色类型（会波及 PATCH / publish / 审核 UI）。
3. **缺口落进候选名单**：同轮复用 propose 三分类把缺的公司写成候选（LLM 永不写白名单，ADR-0001 不变）；候选按公司聚合、证据累积。
4. **圈题闸门按候选状态**：存在待处置候选的条目暂停圈题（防重复烧 LLM）；候选被处置（已入册/忽略）后条目重新可解析，经已发布补救通道补判主导——这就是"入册后徽章自动纠正"的机制。
5. **闭环命令**：一条命令完成"重新生成 registry → 刷新公司镜像并重匹配 → 全量重匹配 → 候选状态回填"。
6. **零数据库迁移**：复用候选表与 `enrich_state` 三档。

## 后果

- 错误主导徽章不再产生；无主导条目仍出现在相关公司页（它们确实被提及），只是无主次标记。
- 无主导条目每次解析多一次 LLM 调用（仅命中该分支时）。
- 候选名单成为"缺公司"的唯一收口：编辑攒证据 → 批量入册 → 一条命令 → 徽章修正。
- 入册后旧归属行不会被删除（既有 upsert 只增改不删），条目会同时挂着新公司与顺带命中公司；主导由后续解析改判——已知遗留，记录在案。
- 若日后要恢复"硬选主导"，删掉无主导分支即可回到 ADR-0014 行为，数据模型不变。
