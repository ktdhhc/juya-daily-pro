# ADR-0016 · 定时链路自动入库（晨间窗口全自动，异常留人工）

- 状态：Accepted
- 日期：2026-09-09
- 关联：ADR-0015（三段制与暂存可见性——本 ADR 修订其「入库恒人工」）、ADR-0008（upsert 幂等）、ADR-0013（本地优先）、spec15（cron 接线）

## 背景

ADR-0015 确立三段制时留了降级路径：「若未来要恢复全自动时效，只需把 publish 挂到解析完成后自动执行，架构不变」。上线首日（2026-09-09）实测暴露了人工环节的实际代价：cron 已把当天 17 条同步进库并完成解析，但停在 `published=0`，事件流与公司页对访客不可见——而日报页直连 daily.juya.uk，看起来「只有日报页更新了」。用户判定该状态下日常流程不应依赖人工点击，提出：

> 改成自动发布，只有在出现意外情况（例如下午更新）时才由我手动同步入库。

## 决策

1. **定时链路自动入库**：`scheduled` 处理程序在同步无失败且本轮有暂存期时，走完解析后按终态自动执行 `reviewPublish`（与审核台「确认入库」同一实现，同一批 SQL 语义：published 0→1 + 应用 proposal + 写 enrich_cache）。
2. **自动入库的闸门（宁留人工，不上错数据）**：
   - 同步存在失败期 → 止步（既有）；
   - 解析作业进行中（未陈旧）→ 整轮跳过（另一轮作业/人工操作在跑，属异常）；
   - 无待解析目标 → 直接入库（不浪费 LLM 调用）；
   - 解析终态 `done` 且非「整轮零成功」→ 入库。个别条目失败仍入库（失败条目不应用建议，按其确定性归属发布）；
   - 终态 `failed` 或「整轮零成功」（`total>0 && processed===0`，LLM 链路疑似故障）→ **不入库**，暂存留人工。
3. **入库范围 = 当前全部暂存期**（`runSyncCore` 的 `stagedDates` 口径，去重升序）。含两层含义：①下一轮 cron 会自愈上一轮因解析失败/中断而未入库的期；②人工暂存但未入库的期也会被下一轮 cron 一并入库——人工链路的「暂存」不再是长期隔离手段，只用于当天下午的例外场景（用户自行发布）。
4. **手动链路语义不变**：`POST /api/sync`（同步按钮/接口）仍只写暂存、`POST /api/parse` 仍只解析、`POST /api/review/publish` 仍是显式入库。审核台从「每日必经」降级为「抽查 + 异常补救」入口。
5. **解析等待方式**：cron 路径调用 `startParse` 时**不传 ctx**（执行体同步 await），以便拿到终态再决定是否入库；HTTP 路径行为不变（`ctx.waitUntil` 异步续跑、秒回）。

## 后果

- 访客时效恢复为「当天自动可见」，不再依赖人工值守；日报页与事件流/公司页的可见性差异在日常情况下消失。
- 新增两类「挂起」状态需要人工关注：同步失败、解析失败/整轮零成功——它们会让当天内容停在暂存（审核台「异常」tab 与同步运行记录可见）。
- cron 单次执行时长从「秒级触发 + 后台解析」变为「同步 + 解析 + 入库全链路 await」（实测本地 30s 级，LLM 并发上限 `MAX_LLM_PER_RUN`）；若解析超出 cron 墙钟上限被中断，`parse_state` 留在 running，下一轮由 10 分钟陈旧自愈接管。
- 决策纯函数 `autoPublishDates`（`worker/api/parse.ts`）进 vitest；本地以 `wrangler dev --test-scheduled` + `/__scheduled` 验收三条分支（解析成功入库 / 无目标直接入库 / 整轮零成功留人工）。
- 若日后要恢复「定时链路也人工确认」，删掉 `scheduled` 中的 `reviewPublish` 调用即可回到 ADR-0015 行为，数据模型不变。
