# 路由结构：三视图静态导出（事件流 + 公司 + 日期阅读）

## Context

最初设计是四路由 `/` `/timeline` `/company` `/company/[id]`，把"日期阅读"与"跨期时间线"作为两个独立视图。审视后发现两者在"按时间倒序看 Item"职能上重叠——日期阅读页本质上就是"某一期的时间线 + 完整正文"，两视图差异只在密度（阅读页有正文 vs 时间线只有卡片）与时间范围（单期 vs 全量）。

把"按时间看"合进单一连续 stream 是一种选择，但用户日常打开 juya-daily 的体感是"看一份今天报"，连续滚会破坏这种"一期一份"的报纸式阅读感。保留单期阅读 + 跨期浏览两视图的拆分，让"读完整一期"与"跨期扫事件"是两种独立工作流，更稳妥，承认两视图职能部分重合是必要代价。

## Decision

三个路由，每个职责单一，URL 可分享。Next.js 16 静态导出原生支持，切换走软导航几乎瞬时。

- `/`                 当前期阅读页（现状不变，`?date=` 同步、保留报纸式单期完整阅读体感）
- `/stream`           事件流视图：跨期 Item 卡片流，按天分组、左侧 facet 筛选（公司 / 分类 / 日期范围）
- `/company`          公司索引页（按字母或事件数排序的卡片墙）
- `/company/[id]`     单公司页（该公司所有事件按时间倒序）

顶部 Header 在四页共用，新增 Nav 三联：`日期 | 事件流 | 公司`，右边保留 ThemeToggle。
首页默认仍是当前期阅读，不打破已有的 `?date=` 分享习惯。

## Why not the alternatives

- **原四路由 `/` `/timeline` `/company` `/company/[id]`**：`/` 与 `/timeline` 在"按时间看 Item"职能上重合，认知成本高、卡片字段两视图共用却两套渲染入口、用户需判断"今天看 / 还是 /timeline"。
- **二路由（合并 `/` 与 stream 为一连续滚）**：抹掉"原期阅读"的报纸式体感，跨期连续滚让用户失去"今天这一份"的边界感。
- **三路由但用 `/timeline` 作路由 slug**：用户对"时间线"的固有期待是 Twitter/微博式纯事件流，与本项目"按天分组卡片+facet 筛选"的形态有歧义；`/stream` 更精准且不与通用"时间线"语义冲突。

## Consequences

- 文档与代码中路由路径统一从 `/timeline` 改为 `/stream`；视图产品命名统一为"事件流"（取代原"时间线视图"）。
- 通用语义"时间线"（如"Kimi IPO 跨日报道聚成一条时间线带子事件"）保留，仅视图名与路由 slug 改名。
- 卡片字段与 `/stream` 视图契约不变（详见 `docs/prd/PRD.md` Implementation Decisions 段）。
- 公司页与首页 `/` 维持原设计。
