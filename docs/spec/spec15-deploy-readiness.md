# Spec 15 · 部署就绪与定时自动化

> 来源：2026-09-06 部署就绪审计（用户要求按固定工作流补齐缺口）。约束：ADR-0010（Pages + 独立 Worker 拓扑）、ADR-0013（部署日集中动作）、ADR-0015（cron 只写暂存，入库人工确认）。
> 测试缝（已与用户确认）：①纯函数缝（脚本命令行目标解析）②Worker 集成缝（定时任务真实触发 + curl 断言）③Pages 代理缝（本地 pages dev 三条 curl）。

## Problem Statement

准备把产品部署到 Cloudflare 时，一连串与功能无关的阻碍浮出水面：部署命令会因一份早已裁剪的存储绑定（R2）而失败；前端部署到 Pages 后没有同域 `/api` 通路，页面会调不到后端；生产环境的「管理口令」并非强制项——一旦忘记设置，任何人都能触发同步、解析和入库；定时自动化完全没接线，上线后每天都要有人手动点「同步」和「解析」；运维脚本只会操作本地数据库，生产环境的首次数据回填做不了。这些问题把「部署日」变成一场临时排障，而不是一次按清单走完的上线。

## Solution

把部署前能在本地完成的事情一次性做完：清理过期配置、补齐 Pages 同域代理、把「同步 → 解析」接到定时触发器上、让运维脚本支持远端目标、把管理口令变成部署强制项。完成之后，部署日只剩需要人在场/账号的动作：登录、建库、填库 id、推送密钥、部署、配置 Pages 变量、迁移首页数据源。

## User Stories

1. 作为部署者，我希望部署命令一条就能成功，而不是被残留的存储绑定挡住。
2. 作为部署者，我希望配置文件里没有无人消费的环境变量，这样参数表就是可信的。
3. 作为站点所有者，我希望生产环境强制要求管理口令，否则拿到地址的人都能触发同步/解析/入库。
4. 作为维护者，我希望每天早上自动跑「同步 + 解析」，这样日报落地不依赖我记着点按钮。
5. 作为维护者，我希望定时任务不自动入库，解析建议仍由我在审核台确认（暂存制不变）。
6. 作为维护者，我希望定时任务的结果落在同步运行记录里，失败也能事后回看，而不是静默。
7. 作为维护者，我希望定时任务与我手动点的解析不打架：解析进行中时定时任务跳过解析。
8. 作为部署者，我希望生产数据库的首次回填能直接跑脚本，不用手工逐条执行 SQL。
9. 作为部署者，我希望脚本默认仍操作本地库（零登录开发流程不变），只有显式指定时才连远端。
10. 作为访客，我希望部署后同域 `/api` 直接可用，不需要额外的跨域配置。
11. 作为部署者，我希望 Pages 只把 `/api/*` 交给代理函数，静态资源直出，不浪费函数调用。
12. 作为部署者，我希望代理配置缺失时看到明确的错误提示，而不是白屏。
13. 作为维护者，我希望同步逻辑在「手动端点」和「定时任务」之间只有一份实现，避免两条路径行为漂移。
14. 作为维护者，我希望这次改动不改变任何既有接口行为，前端与其他调用方零感知。
15. 作为维护者，我希望既有全部测试继续通过，证明重构没有引入回归。
16. 作为部署者，我希望部署清单只剩需要人在场的动作，交接给他人也能照做。
17. 作为维护者，我希望定时频率对齐日报发布窗口（北京时间 8-11 点），不在无人更新时段空转。
18. 作为维护者，我希望没有新内容时定时任务不浪费 LLM 调用（无待解析目标则跳过解析）。
19. 作为维护者，我希望远端回填与本地回填走同一套解析/匹配/写库逻辑，结果一致。
20. 作为未来的我，我希望 spec 明确记录「入库保持人工确认」的原因，避免以后被误改成全自动。

## Implementation Decisions

- **配置就绪化**：移除已裁剪存储的绑定与三个无人消费的变量；把管理口令加入部署必需的密钥清单；启用定时触发器，表达式覆盖北京时间 08-11 点每半点（单条表达式，免费额度内）。
- **同步核心抽取**：把 HTTP 同步端点的主体抽成可复用函数，返回结构化摘要（写入期、三分类、暂存计数、失败清单、耗时）；路由变成薄壳，响应契约逐字段不变。
- **定时任务编排**：调用同步核心 → 无失败且存在待解析目标时，复用既有解析异步作业；解析进行中（未陈旧）则跳过解析；任何异常只记录不向上抛；不触发入库。
- **运维脚本目标切换**：新增一个纯函数解析命令行参数得到数据库目标（本地/远端，缺省本地），五个运维脚本统一透传。
- **Pages 同域代理**：以 Pages Function 把 `/api/*` 转发到 Worker origin（origin 由 Pages 项目变量注入），显式校验路径前缀，原样透传方法与请求体；静态资源不进函数。
- **边界**：不引入新依赖；不改任何既有 API 契约；不新增自动入库路径。

## Testing Decisions

- **好测试的标准**：只验证外部行为，不耦合内部结构——新增单测只针对纯函数；被抽取的同步核心不新写针对内部结构的测试，而以既有 worker 套件零回归作为守门（重构不属于 TDD 循环）。
- **缝 1（纯函数）**：命令行目标解析的纯函数单测，追加在既有的脚本工具测试文件中（既有先例同缝）。
- **缝 2（Worker 集成）**：本地 Worker 以 `--test-scheduled` 启动，触发定时任务后断言同步运行记录增行、解析状态变化、无未捕获异常；沿用既有的 curl 验收惯例。
- **缝 3（Pages 代理）**：本地 `pages dev` 起站点，三条断言——`/api/*` 与 Worker 直连同形、静态路径直出不经函数、POST 透传。
- **防回归**：既有全部用例（363）保持全绿。

## Out of Scope

- 替换数据库 id（部署日登录后）。
- 首页迁移到 read API（部署日；ADR-0013 接受临时口径差）。
- 自动入库/自动发布（保持人工确认，ADR-0015）。
- 通知渠道（邮件 / 即时消息）。
- 同步提速（条件请求复用，另案待定）。

## Further Notes

- 定时触发表达式与部署日清单的对应：部署日启用后，最坏延迟 = 半个触发周期（≤30 分钟）覆盖日报发布窗口。
- 部署日剩余动作：登录 → 建库 → 填库 id → 推送密钥（管理口令 + LLM key）→ 部署 Worker → Pages 项目变量与部署 → 首页迁移。
- 定时任务在免费额度内可行：单条触发器、每日 6 次；写库量与 LLM 调用量均为个位数到十位数级。
- 定时任务的可见性依赖既有「同步运行记录」表与「解析状态」单行表，审核台天然可见，无需新界面。
