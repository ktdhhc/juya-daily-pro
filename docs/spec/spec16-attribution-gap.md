# spec16 · 归属缺口兜底（缺主角 → 候选公司闭环）

> 来源：2026-09-09 生产走查（用户发现"OpenRouter 主导 Inception Labs 新闻"类错误归属，提出"没有正确归属时归入临时名单，攒够了我手动入册再清空"）。
> 约束：ADR-0001（Company Registry 唯一闸门、人工入册）、ADR-0014（单段归属、无 RAG）、ADR-0015/0016（编辑工作流与自动入库）、ADR-0017（本 spec 的决策记录）。

## Problem Statement

当一条 Item 的主角公司**不在 Company Registry**、而正文顺带提到了在册公司时，段一确定性匹配会把条目归属给这些"顺带公司"，第二段 LLM 又被强制从候选中挑一个当主导（响应校验要求 `primary_company_id` 必须 ∈ 候选 id）——于是事件流与公司页出现"OpenRouter 主导 Inception Labs 新闻"这类明显错误的徽章。这类条目同时**不会进入任何候选名单**（只有零命中条目才会被提议候选），编辑既看不到"缺哪家公司"，也无法把它攒进"临时名单"批量入册。

生产实测（1265 条已发布）：零命中 135 条（已被现有候选流程覆盖）；多家命中 374 条，其中 **73 条标题里不出现任何命中公司**（"主角可能缺席"的上界，即本 spec 要兜底的类）。

## Solution

给归属链路加一条"主角缺席"兜底：

1. 解析段允许 LLM 判定"候选清单里没有主角"。判无主导的条目**不再硬选主导**——保留段一命中的归属（仍出现在相关公司页），但角色全部留空（无主次徽章），照常入库。
2. 同一轮判定里，把"缺的那家公司"按既有 propose 三分类落进**候选公司名单**（编辑口中的"临时名单"），证据累积，攒够后由编辑人工入册。
3. /review 把这类条目收进「缺候选待入册」，候选区显示累积证据；候选可「标记已入册 / 忽略」。
4. 提供一条命令完成"入册 → 重匹配 → 候选状态回填"；随后既有解析通道自动补判主导，错误徽章被纠正。

编辑的日常因此变成：**攒证据 → 一次性入册 → 一条命令 → 徽章自动修正**，而不是逐条发现错误归属。

## User Stories

1. 作为站点读者，我希望事件流里的条目不再出现"顺带提到的公司当主导"的错误徽章，这样我对归属信息的信任不被打折。
2. 作为编辑，我希望系统在判定"主角不在白名单"时明确给出这个结论，而不是硬选一个候选当主导。
3. 作为编辑，我希望这类条目自动把"缺的那家公司"记进候选公司名单，这样我不必逐条人工发现缺口。
4. 作为编辑，我希望候选名单按公司聚合而不是按条目罗列，这样我能一眼看出哪家公司被反复提到、值得入册。
5. 作为编辑，我希望候选条目上的证据会累积，这样"攒到一定程度"有据可依。
6. 作为编辑，我希望在 /review 的「缺候选待入册」里看到这类条目，知道它们卡在哪一步。
7. 作为编辑，我希望入册一家公司后，名单里对应的候选自动标记为已入册，不需要我手工比对清单。
8. 作为编辑，我希望入册并重匹配后，相关条目的主导被自动补判为新入册的公司，这样旧条目的错误主导会被纠正。
9. 作为编辑，我希望有一个"忽略"动作，把不打算入册的候选移出名单。
10. 作为编辑，我希望无主导的条目仍然挂在相关公司页（它们确实被提到），只是不带主导徽章。
11. 作为编辑，我希望自动入库链路不受影响：无主导条目照常入库，不会因为缺主导而卡住当天内容。
12. 作为编辑，我希望已提议候选的条目不会每轮重复烧 LLM，直到候选被处置。
13. 作为编辑，我希望"在册公司的产品/子品牌"不会被误记成新公司候选。
14. 作为运维，我希望这条链路不引入数据库迁移，降低上线风险。
15. 作为编辑，我希望一条命令完成"入册 → 重匹配 → 候选状态回填"，不用记四条命令。
16. 作为编辑，我希望单条 LLM 响应不合法时按单条失败记账，不阻塞整批解析。
17. 作为编辑，我希望已发布条目的主导纠正继续走既有补救通道，不需要新机制。
18. 作为读者，我希望无主导条目的标题、摘要、公司链接照常可读。
19. 作为未来的我，我希望这套机制有 ADR 与文档记录，避免被后来的改动悄悄破坏。
20. 作为未来的我，我希望文档说明"为什么无主导不落归属建议"，避免后人改回硬选。

## Implementation Decisions

**术语**：候选公司（Company Candidate）= 编辑口中的"临时名单"；无主导判定 = 解析段对某条目得出"候选清单中没有主角"的裁决。

1. **enrich 段新增「无主导」裁决**：主导判定 prompt 增加规则——若条目主体公司不在候选清单中，`primary_company_id` 返回 `null`；响应解析必须区分两种失败：**响应不合法**（非法 JSON / 幻觉 id / 缺 reason）与**合法判定无主导**（`primaryId: null` + 非空 reason）。角色推导只在有主导时执行。
2. **无主导 → 复用 propose 三分类**：同一作业槽内对同一条目再跑一次 propose（复用既有 prompt 与解析纯函数，不新增 prompt 资产）。裁决为"新公司"→ 写候选公司；"在册公司产品"或"无关"→ 不写候选。成本：仅无主导条目多一次 LLM 调用。
3. **无主导不落归属建议（proposal）**：条目保持段一命中的归属行、角色全部留空；入库走"无建议"路径（既有语义：按当前归属直接发布）。理由：归属建议的角色是必填枚举，为"无主导"扩展类型会波及 PATCH / publish / 审核 UI 三处；不落建议同时让"建议"在审核台保持"有可应用内容"的干净语义。
4. **解析圈题闸门**：存在**未入册候选**（待处置 pending 或已忽略 dismissed）的条目不再圈题（零命中与多家命中皆然），避免每轮重复调 LLM；候选一旦标记为**已入册**，闸门解除、条目重新可解析——这是"入册后自动改判主导"的通道。判定两条并行：①候选表来源条目字段直接指向的条目；②标题/正文提到某个未入册候选公司名的条目（候选按公司聚合只保留一个来源条目，光靠 ① 盖不住同一家公司被多条提及的情形——code-review P1 补正；已忽略的候选同样挂闸门，否则用户表态后仍每轮重烧 LLM）。
5. **候选证据累积**：候选写入从"已存在即跳过"改为**合并证据**（reason 去重追加、最多保留 5 段，首个来源条目 id 作为溯源保留）。"攒够"由编辑看证据段数判断，不新增计数字段。
6. **审核台分组扩展**：多家命中且存在待处置候选的条目归入「缺候选待入册」（该 tab 原本只收零命中条目）；候选区展示合并后的证据。
7. **候选状态端点**：新增管理员端点，请求体 `{id, status: "registered" | "dismissed"}`；校验 + SQL 生成走纯函数；状态变更只改候选表，不触碰 Registry。
8. **入册闭环命令**：一条 npm script 串起——① 从 `data/companies.yaml` 重新生成 registry ② 刷新 D1 公司镜像并做窗口重匹配 ③ 全量重匹配（覆盖窗口外的历史条目）④ 把"新 registry 里已存在"的待处置候选回填为已入册（纯函数判定）。命令**不触发解析**（用户 2026-09-09 决策）：结束时提示"下一轮定时任务或手动「运行解析」会经已发布补救通道补判主次"。
9. **无数据库迁移**：复用既有候选表与 enrich_state 三档，不改 CHECK 约束、不加列。
10. **不变式（沿用）**：LLM 永不写白名单（候选只落候选表）；入册唯一通道仍是人工编辑 yaml；入库仍是 published 0→1 的原子批；同步段仍零 LLM。

## Testing Decisions

- **什么算好测试**：只验证公共接口的**外部行为**——给定条目与候选清单，观察裁决/候选/分组/SQL 产物；不断言内部调用顺序，不 mock 内部协作者，期望值取自 spec 的规则而非重算实现。
- **被测模块（纯函数缝，既有 vitest 套件）**：
  - 主导判定与响应解析：prompt 是否包含"无主导"规则；`primaryId: null` 与"响应不合法"两条路径可区分。
  - 解析圈题：pending 候选跳过、非 pending 不跳过。
  - 候选写入 SQL：证据合并去重、段数上限、溯源保留。
  - 候选状态校验与 SQL 生成。
  - 审核台分组：多家命中 + 待处置候选 → 缺候选待入册。
  - 闭环命令的"该标记哪些候选"判定纯函数。
- **先例**：`src/lib/llm/enrich.test.ts`、`worker/api/parse.test.ts`、`src/lib/review.test.ts`、`scripts/lib/wrangler-cli.test.ts`（均为纯函数 + 已知期望值）。
- **集成验收（既有缝 2）**：`wrangler dev --test-scheduled` 触发定时链路 + 直读 D1——验证"判无主导 → 不写建议、候选落库、条目照常入库"与"入册重匹配 → 候选转已入册 → 条目重新可解析"。
- **UI**：/review 候选区与分组只做浏览器人工走查（仓库无组件测试基建，不为它新建）。

## Out of Scope

- 已发布条目改归属的 UI（继续走 `enrich --apply` 命令行通道）。
- 自动入册 / LLM 直接写白名单（ADR-0001 不变）。
- 新增 `enrich_state` 档位或数据库列（保持三档、零迁移）。
- 候选的排序/优先级策略（沿用 id 序）。
- "在册公司产品 → 加 alias"建议的落地通道（本版 product 分支仍只计数，不落候选）。
- 首页迁移 read API、自定义域名（既有待办，与本 spec 无关）。

## Further Notes

- 本 spec 的决策记录在 ADR-0017；术语补充（候选公司 = 临时名单）进 CONTEXT.md。
- 与自动入库（ADR-0016）的关系：无主导条目照常入库（不会因缺主导挂起），因此"事件流当天可见"的时效不变。
- 已知遗留：入册后旧归属行不会被删除（upsert 只增改不删），条目会同时挂着新入册公司与原先顺带命中的公司；主导由后续解析改判。这是既有 upsert 语义，不在本 spec 修。
- 已知遗留（pre-existing）：propose 裁决为 `product`/`ignore` 的条目不产生候选行，因此没有闸门可挂，每轮解析仍会重判（与零命中 missing_owner 的既有行为一致）。本 spec 未改，如需收敛另立票。
- 生产存量参考：零命中 135 条、多家且标题无命中 73 条（2026-09-09 实测），本 spec 上线后这两类都有明确去处。
