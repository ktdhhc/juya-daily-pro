## 一、固定工作流（每个阶段都这样跑，已被 7 个 spec 验证）

1. **to-spec**：在 `docs/spec/spec<NN>-<slug>.md` 写工程性 spec（可线性执行：目标 / 前置事实（**必须实测核验后写入**）/ 分步骤（每步带验证命令）/ 验收清单 / 边界）。不是产品文档。
2. **to-issues**：拆票到 `.scratch/<spec-name>/issues/<NN>-<slug>.md`，每票自带 Status 行 + 验收标准 + Blocked by。
3. **subagent TDD**：一般 agent 不能调 skill，派工 prompt 必须显式写清 TDD 红绿纪律（"先写测试记录失败输出=红，再最小实现转绿，禁止先实现后补测试"）+ 允许/禁止文件清单 + "不要 git commit" + 汇报格式。文件不相交的票**并行派多个 agent**（同工作区注意：写 package.json 的票不可并行、并发 `next build` 会撞 `.next`——约定"EPERM 等 90s 重试一次"）。
4. **主会话权威验收**：不采信 agent 自报，四门禁（test/typecheck/lint/build）独立复跑 + D1 查询对账。
5. **code-review 每 spec 一次**：写 `.scratch/<spec>/review.md`，P0-P3 分级；P0/P1 追加票派 subagent 修；**一个 spec 只 review 一轮防死循环**。
6. **收尾**：更新 `docs/CURRENT_STATE.md`（它有覆盖式更新的维护规则）→ 提交（实现与 docs 可分两笔）。
7. 浏览器验证（有 UI 的 spec）：**截图看视觉、domSnapshot/evaluate 看结构与行为**；坐标点击不可靠时用页面内 evaluate 直接触发；IAB 卡死先查 8787 是否被 wrangler 僵尸进程霸占（历史教训见 spec06 review）。

纪律要点（全部踩过坑换来的）：agent 汇报与实测冲突时以实测为准；spec 前置事实写错要当场修正（历史上 importer 数、site-badge 变体数都错过）；变异验证证明测试咬合；纯函数优先（ADR-0011）；每轮收尾 `git status` 必须干净。
